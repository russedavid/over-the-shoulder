# Local OCR options for Over The Shoulder Coder

Research checked September 9, 2026. The target machine reports an **Apple M3 Max, 48 GiB unified memory, and macOS 15.6.1**. The requirement is accurate screen/code transcription with separately addressable text regions, suitable for highlighting and displaying each region independently.

The strongest next experiments are **GLM-OCR**, **PaddleOCR-VL-1.6**, and **Granite Docling** for recognition, with **PP-OCRv6** as the fast detector/recognizer comparison. **ScreenVLM** deserves a separate layout experiment because its training target is UI screenshots. These are researched candidates; none was newly benchmarked on our recordings during this research pass. The existing Tesseract/Apple Vision measurements remain in [the OCR findings](ocr-vlm-tradeoffs.md).

Subsequent result: the [GLM-OCR local trial](glm-ocr-trial.md) failed the automatic IDE OCR requirements. It read manually selected code quickly, but its layout stage failed to separate panes, full-screen extraction lost diff changes, and code crops included IDE annotations. The research shortlist is not evidence of successful integration.

These are different kinds of systems. Docling and MinerU are frameworks/pipelines; MLX and llama.cpp are runtimes; PP-DocLayoutV3 is a layout detector. A framework using the same recognition weights is not an independent OCR model in a benchmark.

## What the headline scores establish

OmniDocBench covers document text, formulas, tables and reading order. Its versions and matching procedures changed; its current repository includes a `v1.6_full` table with PaddleOCR-VL-1.6 at 96.34 and GLM-OCR at 95.22. OvisOCR2's 96.58 is its publisher's reported v1.6 result. Preserve the exact benchmark version, pipeline and evaluator when comparing these numbers; none measures code-symbol accuracy in our IDE captures. [Benchmark owner](https://github.com/opendatalab/OmniDocBench), [OvisOCR2 report](https://arxiv.org/abs/2607.13639).

More directly relevant evaluation sources:

- **CodeSCAN** describes 12,000 VS Code screenshots spanning 24 languages, 25 fonts and over 90 themes, with IDE-element detection and OCR evaluation. Its scenario design is much closer to our screen use case; confirm dataset/code access and licensing before importing data. [Paper](https://arxiv.org/abs/2409.18556).
- **CHAOS-Bench** deliberately changes characters in document images to test whether an OCR VLM copies visible but linguistically implausible text or silently corrects it. That is relevant to preserving unusual identifiers and actual code mistakes. It is not an IDE benchmark. [Publisher benchmark](https://github.com/Tencent-Hunyuan/HunyuanOCR/tree/main/benchmarks/CHAOS-Bench).
- **OCRBench v2** evaluates localization/spotting as well as recognition and reasoning; it provides a broader cross-check than a PDF-only leaderboard. [Benchmark authors](https://99franklin.github.io/ocrbench_v2/).

Throughput, first-token latency and complete-frame latency are different measurements. A small model generating thousands of tokens can still be slow. A figure-box variant is not a text-box detector. A model that fits in memory is not necessarily supported or fast in the chosen Metal runtime.

## Proposed evaluation order

1. Run PP-OCRv6 and GLM-OCR on the same original IDE images, preserving detected text regions. Compare with the already measured Tesseract and Apple Vision baselines.
2. Test Granite Docling's code task on detected code crops, and its structured page output separately. Include PaddleOCR-VL-1.6 as a compact high-quality pipeline comparison.
3. Test ScreenVLM specifically on pane/element separation. Do not assume a web-trained parser understands native IDE panes; judge those boxes against the screenshot.
4. Add OvisOCR2 or LightOnOCR-2 behind the same detector if recognition remains the limiting factor. DeepSeek-OCR-2, HunyuanOCR-1.5, dots.mocr and MinerU are further alternatives rather than prerequisites to the first experiment.

For each run, retain raw output, model revision, backend, precision, prompts, image bytes and coordinate transforms. Measure full-frame latency, cold/warm behavior, peak memory and interaction with local ASR. Start with an unquantized compact checkpoint where practical; quantization can be evaluated separately rather than assumed harmless to glyph recognition.

Score exact identifiers, numbers, operators, braces, indentation and missing/invented lines. Measure whether text is assigned to the correct box, whether columns get mixed, and whether boxes remain useful after scrolling/resizing. Word recall alone can miss `!==` becoming `!=` or `DTO` becoming `DT0`. Keep the existing eight recorded sessions as development material and use unseen screenshots for the final assessment.

## Integration direction

Keep detection and transcription results as structured regions through the existing Python application. Preserve a region ID, source frame, rectangle/polygon, text lines and recognition uncertainty. Render each region independently and link it to an overlay on the original screenshot. Normalize model coordinates back to that original frame; different candidates use pixels, 0–500 or 0–1000 coordinates.

Benchmark experiments can use isolated environments without committing to a new desktop architecture. The selected OCR implementation should fit into the existing capture/context workers and retain the current proposal, provenance and stale-response behavior. This research does not replace the live OCR engine or modify model settings.
